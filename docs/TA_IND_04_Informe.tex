% Introducción
\section{Introducción y contexto}

El procesamiento paralelo y distribuido permite repartir una carga de trabajo
entre varias unidades de cómputo. Sin embargo, aumentar la cantidad de recursos
no garantiza una reducción proporcional del tiempo de ejecución. En Apache
Spark, la cantidad de executors constituye un parámetro relevante y una
asignación inadecuada puede producir un uso poco eficiente de los recursos o
un mayor tiempo de ejecución \cite{sen2021}. Asimismo, el ajuste de los
parámetros de configuración de Spark constituye un problema de optimización
que depende de las características de cada aplicación \cite{cheng2021}.

El presente informe analiza de manera individual los resultados obtenidos en la
práctica PE-U4. En el experimento se implementaron cinco transformaciones
equivalentes mediante pandas y PySpark sobre un conjunto sintético de
\num{500000} solicitudes y 14 columnas. Para cada configuración se realizaron
cinco repeticiones y se utilizó la mediana como tiempo representativo. Antes de
las repeticiones registradas se descartó una ejecución inicial de calentamiento.

La transformación seleccionada como foco individual es T1, correspondiente al
filtrado y selección. Esta operación procesa los \num{500000} registros de
entrada y produce \num{33117} registros como resultado.

Los datos utilizados son trazables al repositorio PE-U4 del Equipo C:

\begin{center}
\url{https://github.com/ffarinangog2/pe-u4-spark-equipo-c}
\end{center}

\noindent
Las mediciones adicionales de T1 con uno y dos executors se incorporaron en el
commit:

\begin{center}
\texttt{\footnotesize 6b363abdd30e57425fc8e49a9a13181c2cb2a5b9}
\end{center}

\noindent
Los resultados se encuentran registrados en
\path{resultados/tiempos_crudos.csv} y
\path{resultados/tiempos_resumen.csv}.

El entorno documentado en el proyecto utiliza PySpark 3.5.0, Python 3.12.10,
OpenJDK 17.0.20 y Windows 11. Spark fue ejecutado en modo Standalone con el
master \url{spark://127.0.0.1:7077}. Cada executor fue configurado con un
core y \SI{512}{\mebi\byte} de memoria. Además, el número de particiones, el
paralelismo por defecto y el máximo de cores se ajustaron al número de
executors utilizado en cada configuración.

Cheng et al. estudian el ajuste de parámetros de Spark mediante modelos de
predicción y optimización del rendimiento \cite{cheng2021}.

Para estudiar el escalado de T1 se toma como referencia la ejecución Spark con
un executor:

\[
T_1=\SI{0.3134846}{\second}.
\]

Los resultados obtenidos fueron los siguientes:

Para dos executors:

\[
S(2)=
\frac{T_1}{T_2}=
\frac{0.3134846}{0.8624843}=

\]

Para cuatro executors:

\[
S(4)=
\frac{T_1}{T_4}=
\frac{0.3134846}{0.3456639}=

\]

En ninguna de las configuraciones se obtuvo una aceleración respecto de la
ejecución con un solo executor. La configuración con dos executors presentó el

Sus cinco tiempos fueron \SI{0.8624843}{\second},
\SI{0.3758325}{\second}, \SI{1.1714799}{\second},
\SI{0.2754539}{\second} y \SI{1.4906592}{\second}. La diferencia entre el
menor y el mayor valor evidencia una variabilidad considerable en esta
configuración.

\subsection{Contraste con la Ley de Amdahl}

La Ley de Amdahl establece el límite del speedup que puede alcanzarse cuando
una fracción $p$ de un programa puede ejecutarse en paralelo
\cite{amdahl1967}:

\begin{equation}
S(N)=
\frac{1}
{(1-p)+\dfrac{p}{N}},
\qquad
S_{\max}=
\lim_{N\rightarrow\infty}S(N)=
\frac{1}{1-p}.
\label{eq:amdahl}
\end{equation}

El experimento no midió de forma independiente la fracción paralelizable $p$.
Por ello, se utiliza $p=1$ únicamente como una referencia ideal superior, es
decir, como el caso en el que no existe fracción serial ni sobrecarga. Esta
elección no implica afirmar que T1 sea completamente paralelizable durante una
ejecución real.

Bajo esta referencia ideal:

\[
S_{\text{teo}}(N)=N.
\]

Para dos executors, la desviación relativa entre el valor medido y la
referencia ideal es:

\[
\Delta_2=
\frac{S_{\text{med}}-S_{\text{teo}}}
{S_{\text{teo}}}
\times100=
\frac{0.3635-2}{2}\times100=
-81.83\%.
\]

Para cuatro executors:

\[
\Delta_4=
\frac{0.9069-4}{4}\times100=
-77.33\%.
\]

Por tanto, los resultados experimentales se encuentran claramente por debajo
del límite ideal de Amdahl. El speedup real es menor que uno tanto con dos como
con cuatro executors.

Esto no contradice la Ley de Amdahl. La ecuación representa un límite superior
bajo el supuesto de que el paralelismo no introduce sobrecargas adicionales.
Una ejecución real de Spark incluye planificación, coordinación y distribución
de tareas, por lo que puede producir un speedup inferior a uno cuando dichos
costos superan el beneficio del trabajo paralelo.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.82\textwidth]{fig_speedup.png}
    \caption{Speedup experimental de T1 frente al límite ideal de Amdahl. Elaboración propia.}
    \label{fig:speedup}
\end{figure}

La Fig.~\ref{fig:speedup} muestra que el comportamiento experimental se
encuentra considerablemente por debajo del límite ideal. Con dos executors se
produce una caída marcada del rendimiento y, aunque con cuatro se observa una
recuperación, el speedup permanece por debajo de uno.

% Diagnóstico
\section{Diagnóstico de la fracción no escalable}

La métrica de Karp-Flatt permite estimar experimentalmente la fracción no
escalable a partir del speedup observado y del número de unidades de
procesamiento \cite{karpflatt1990}:

\begin{equation}
e=
\frac{
\dfrac{1}{S}
-
\dfrac{1}{N}
}
{
1-\dfrac{1}{N}
},
\qquad N>1.
\label{eq:karp}
\end{equation}

Aplicando la Ec.~\eqref{eq:karp} para dos executors:

\[
e_2=
\frac{
\dfrac{1}{0.3635}
-
\dfrac{1}{2}
}
{
1-\dfrac{1}{2}
}
\approx
4.5026.
\]

Para cuatro executors:

\[
e_4=
\frac{
\dfrac{1}{0.9069}
-
\dfrac{1}{4}
}
{
1-\dfrac{1}{4}
}
\approx
1.1369.
\]

Los valores obtenidos son superiores a uno. En estas condiciones no deben
interpretarse como una fracción serial física convencional, puesto que el
speedup observado es inferior a uno y la ejecución paralela presenta una
penalización respecto de la referencia.

Además, $e$ disminuye de \num{4.5026} con dos executors a \num{1.1369} con
cuatro. Por tanto, la pérdida observada no se comporta como una fracción serial
aproximadamente constante. La configuración con dos executors presenta una
penalización particularmente alta.

\subsection{Sobrecarga observada}

El primer mecanismo relacionado con los resultados es la planificación y
coordinación del trabajo. Spark debe distribuir las tareas entre los recursos
disponibles y el nivel de paralelismo seleccionado puede influir en el tiempo
total. Sen et al. estudian específicamente la selección del número de
executors para consultas Spark SQL y muestran que distintas consultas pueden
requerir diferentes niveles de paralelismo \cite{sen2021}.

El segundo mecanismo corresponde a la configuración de recursos. En el
experimento, \texttt{spark.executor.instances},
\texttt{spark.cores.max},
\texttt{spark.sql.shuffle.partitions} y
\texttt{spark.default.parallelism} se modifican de acuerdo con el número de
executors. Cheng et al. muestran que la configuración de Spark tiene una
influencia significativa sobre su rendimiento y plantean su ajuste como un
problema de optimización \cite{cheng2021}.

El tercer elemento es la variabilidad observada en las propias mediciones. Con
dos executors se registraron tiempos comprendidos entre aproximadamente
\SI{0.275}{\second} y \SI{1.491}{\second}. Esta dispersión muestra que la
configuración no presentó un comportamiento estable durante las cinco
repeticiones.

La eficiencia del paralelismo se determina mediante:

\begin{equation}
E(N)=\frac{S(N)}{N}.
\label{eq:eficiencia}
\end{equation}

Para dos executors:

\[
E(2)=
\frac{0.3635}{2}
=
0.1817.
\]

Para cuatro executors:

\[
E(4)=
\frac{0.9069}{4}
=
0.2267.
\]

Por tanto, la eficiencia fue aproximadamente
\SI{18.17}{\percent} con dos executors y
\SI{22.67}{\percent} con cuatro. Aunque la configuración de cuatro executors
mejora respecto de la de dos, ambas se encuentran lejos del comportamiento
ideal.

\section{Propuesta de integración al PFC}

En el PFC Tienda Tech, el procesamiento distribuido se propone para el análisis
histórico de pedidos, ventas y movimientos de inventario. No se plantea su uso
dentro del flujo transaccional encargado de registrar directamente una compra,
debido a que este proceso requiere una respuesta inmediata y trabaja con una
cantidad reducida de información por solicitud.

La integración se realizaría mediante procesamiento por lotes. De forma
periódica se extraerían de PostgreSQL los registros históricos necesarios y se
entregarían a un proceso Spark. Este proceso podría agrupar las ventas por
producto y período, analizar el movimiento del inventario y generar indicadores
de demanda.

La salida sería almacenada como información analítica preparada para consulta.
El módulo de reportes utilizaría estos resultados para evitar el procesamiento
completo del histórico cada vez que un usuario solicite información.

La decisión funcional soportada por esta integración sería la priorización de
la reposición del inventario. A partir de los resultados podrían identificarse
productos con alta demanda, bajo movimiento o necesidad de reposición.

Se propone una ejecución por lotes debido a que este procesamiento no necesita
realizarse durante la compra de un cliente. La tarea podría ejecutarse
periódicamente una vez acumulada nueva información.

% Dimensionamiento
\section{Dimensionamiento y viabilidad}

El modelo para estudiar la rentabilidad del procesamiento distribuido
considera un tiempo secuencial:

\[
T_{\text{sec}}(n)=\alpha n,
\]

y un tiempo distribuido:

\[
T_{\text{dist}}(n)=
\beta+
\frac{\gamma n}{N}.
\]

El umbral de rentabilidad se expresa mediante:

\begin{equation}
n^{*}=
\frac{\beta}
{\alpha-\dfrac{\gamma}{N}},
\qquad
\alpha>
\frac{\gamma}{N}.
\label{eq:umbral}
\end{equation}

Los parámetros $\alpha$, $\beta$ y $\gamma$ deben obtenerse mediante un ajuste
sobre mediciones experimentales. Los datos disponibles para T1 corresponden a
un único volumen de \num{500000} registros, lo que impide identificar de forma
independiente y confiable los tres parámetros del modelo mediante un ajuste
por mínimos cuadrados: se necesitarían al menos tres pares $(n,T)$ distintos
con $N$ constante para ese fin.

No obstante, es posible utilizar los tres tiempos disponibles de T1
($N=1,2,4$, con $n$ constante) para diagnosticar el signo del término
paralelo. Si se despeja $\gamma$ a partir de dos de las mediciones con $n$
fijo, por ejemplo $N=1$ y $N=4$:

\[
\gamma=
\frac{(T_4-T_1)\,N_1 N_4}{n\,(N_1-N_4)}
=
\frac{(0.3456639-0.3134846)(1)(4)}{500000\,(1-4)}
\approx
-8.58\times10^{-8}\ \text{s/registro}.
\]

El valor de $\gamma$ resulta negativo, lo cual carece de sentido físico bajo
el modelo propuesto y confirma que, en el rango de $N$ evaluado, la sobrecarga
fija $\beta$ domina sobre el término paralelo $\gamma n/N$: el tiempo de Spark
no decrece de forma consistente al aumentar $N$, por lo que el modelo lineal
no puede ajustarse de manera fiable con la evidencia disponible.

Aun así, puede obtenerse una \emph{cota inferior optimista} de $n^{*}$
aproximando $\beta\approx T_{\text{spark}}(N=4)$ y despreciando el término
$\gamma n/N$ (es decir, asumiendo el caso más favorable para Spark, en el que
el costo marginal por registro es nulo). Con
$\alpha=T_{\text{pandas}}/n=\SI{0.2119435}{\second}/\num{500000}\approx
4.2389\times10^{-7}\ \text{s/registro}$:

\[
n^{*}\gtrsim
\frac{\beta}{\alpha}
\approx
\frac{0.3456639}{4.2389\times10^{-7}}
\approx
\num{815000}\ \text{registros}.
\]

Este valor debe leerse estrictamente como una cota inferior, no como una
predicción precisa: al ignorar el costo marginal por registro del motor
distribuido, subestima $T_{\text{dist}}(n)$ para $n$ grande, de modo que el
umbral real de rentabilidad sería mayor. Utilizar las configuraciones de uno,
dos y cuatro executors como si representaran distintos valores de $n$ no sería
correcto, ya que en esas pruebas cambia $N$, pero el volumen de entrada
permanece constante; por ello la cota anterior usa únicamente la
configuración de cuatro executors y el tiempo de pandas, y no un ajuste sobre
los tres puntos de escalado.

Para determinar $n^{*}$ con precisión sería necesario repetir T1 con varios
tamaños de entrada y mantener controladas las demás condiciones del
experimento. Gulino et al. estudian modelos para predecir el tiempo de
ejecución de aplicaciones Spark considerando características del volumen
procesado y los recursos asignados \cite{gulino2020}. De manera relacionada,
Lattuada et al. estudian la asignación de recursos en aplicaciones Spark
mediante modelos orientados a cumplir objetivos de rendimiento
\cite{lattuada2020}.

Mientras no se determine experimentalmente dicho umbral con datos
multi-volumen, para cargas cercanas a \num{500000} registros se mantendría una
solución basada en pandas o consultas SQL, debido a que T1 no presentó una
ventaja de rendimiento mediante Spark y la cota obtenida sugiere que el punto
de equilibrio, de existir en este entorno, se encuentra por encima del volumen
evaluado.

Para una futura implementación, el procesamiento distribuido se ejecutaría
como una tarea independiente por lotes. Entre los principales riesgos se
encuentran la variabilidad del rendimiento, el costo de mantener
infraestructura adicional, un crecimiento de datos insuficiente para justificar
Spark y la sincronización de la información procedente de distintos
microservicios.

% Postura crítica
\section{Postura crítica y alternativas}

Las mediciones disponibles indican que Spark no es actualmente la opción más
eficiente para T1 con \num{500000} registros. pandas obtuvo una mediana de
\SI{0.2119435}{\second}, mientras que Spark con cuatro executors necesitó
\SI{0.3456639}{\second}. Esto produjo un speedup de \num{0.6131}.

La evidencia experimental también muestra que aumentar la cantidad de
executors no produjo una mejora progresiva. Sen et al. señalan que el nivel
adecuado de paralelismo depende de la consulta ejecutada y que la asignación
del número de executors influye en el rendimiento y la utilización de recursos
\cite{sen2021}.

Una primera alternativa es utilizar \textbf{pandas}. Para el volumen evaluado,
esta opción obtuvo un menor tiempo y evita parte de la coordinación requerida
por un motor distribuido.

La segunda alternativa consiste en utilizar \textbf{PostgreSQL} para
operaciones de filtrado y agregación cuando el volumen pueda procesarse de
forma adecuada directamente en la base de datos. Esta opción evita introducir
un componente adicional en la arquitectura para cargas que todavía no
requieren procesamiento distribuido.

Spark se reservaría para escenarios donde el crecimiento de los históricos de
pedidos, ventas e inventario haga insuficiente una solución basada en un solo
nodo. Antes de adoptarlo sería necesario realizar pruebas con diferentes
volúmenes para comprobar que el paralelismo compensa la sobrecarga introducida.

Por tanto, Spark puede considerarse una alternativa para el componente
analítico futuro de Tienda Tech, pero las mediciones actuales no justifican
utilizarlo para T1 bajo las condiciones evaluadas.

% Conclusiones
\section{Conclusiones}

La transformación T1 no obtuvo una aceleración al incrementar el número de
executors. Tomando como referencia Spark con un executor, el speedup fue
\num{0.3635} con dos executors y \num{0.9069} con cuatro. Ambos valores fueron
inferiores a uno, por lo que agregar recursos no redujo el tiempo respecto de
la configuración base.

La métrica de Karp-Flatt produjo valores de \num{4.5026} para dos executors y
\num{1.1369} para cuatro. Estos resultados, junto con la dispersión de los
tiempos observada con dos executors, indican que la ejecución estuvo fuertemente
afectada por costos adicionales y que la pérdida de rendimiento no puede
explicarse únicamente mediante una fracción serial constante.

Finalmente, Spark tendría mayor sentido en Tienda Tech como componente de
procesamiento por lotes para históricos de pedidos, ventas e inventario que
como parte del flujo transaccional. Sin embargo, antes de adoptarlo debe
determinarse experimentalmente el volumen a partir del cual la distribución
resulta rentable mediante nuevas mediciones con distintos tamaños de entrada.
